# Preparation and claim boundaries

Preparation is strategy only, with explicit Human Review required before adoption. Do not edit original CVs, fact cards or canonical files. Select an existing CV Base by exact reference (CN-P/Product, CN-R/Research, General or known adapter); if only its name is known, recommend that route but leave source/version UNKNOWN. Do not manufacture a template or second Base lifecycle.

Every proposed material claim must have:

`JD Requirement → Existing Evidence → Verified Fact → Claim`

Each link needs IDs/locations and scope. Verify the fact itself, personal/team/AI ownership, metric scope and resume-use permission. A true fact with UNKNOWN resume-use remains a review issue, not an approved claim; public-use permission is separately needed for a public artifact. If a link breaks, record a gap and honest response. Wording may clarify a fact but cannot add SQL, experiments, commercial launch, users, efficiency or ownership. A future measurement plan is labelled hypothetical, never historical results.

Evidence-based quantification follows this priority when supported: real outcome numbers → project scale → participant/user count → research/test count → prototype/iteration rounds → process complexity → coverage → real launch/deployment → verified adoption by a partner/team/institution → demonstrable effect on product judgment or later decisions. If real outcome numbers do not exist, use supported scope, complexity, implementation, adoption and decision impact instead of manufacturing metrics. Never invent conversion rate, ROI, user growth, efficiency-improvement percentages or any unrecorded outcome number.

Route only the smallest useful evidence set. Use one role-specific strategy unless the caller supplies separate, reviewed role evidence. Product or business-unit scenarios remain hypotheses until tied to actual role/team evidence. Do not create speculative parallel CVs. Respect caller-supplied location, slot and batch constraints; a backup discussion is not a simultaneous application slot.

Optional VibeCodedProjectEvidencePacket is generated only when this target is likely to question AI-assisted build, prototype ownership, Human-AI product judgment or product/technical boundaries AND relevant completed evidence exists. No default packet per application. Each field cites evidence or stays UNKNOWN: user/problem, why selected, end-to-end flow, product decisions, technical/implementation decisions, AI contribution, human contribution, team contribution, testing/evaluation, discovered problems, iteration, real feedback, approved demo/screenshots/repo/video references, likely objections and evidence-backed answer boundaries.

Packet is a derivative, not a truth source. AI-assisted implementation ≠ Software Engineering; AI used to build ≠ AI runs inside the product. Keep intended workflow, simulated behavior, optional integration and verified runtime behavior separate. Missing demos do not trigger new projects. An aggregate iteration count must link to its accepted aggregate record; if event-level records are absent, label the event trace UNKNOWN and do not invent it. Never equate a prototype demo deployment with commercial production adoption or efficiency improvement. Caller-owned portfolio and project outputs stay read-only.
